## Implementation spec

New crate `crates/backup` (backup sets, parts, schedules, restore orchestration) plus the admin section `/backups`. It uses `crates/storage` for the destination (local volume or S3-compatible bucket), `crates/events`, `crates/audit` and the existing database connection for export and import.

### Scope (in / out)

**In**

- Backup parts, each producing its own artifact and checksum: **database** (logical export of the platform tables), **media** (object listing + copy of the library to the destination),
 **configuration** (selected settings tables exported as JSON — never secret values),
 **themes** (active theme directory + manifest versions), **plugins** (installed component manifests and versions; an empty, honest result until a package installer exists).
- Backup kinds: manual (one click, options in a drawer) and scheduled.
- Schedules: hourly, daily, weekly, monthly — with a time-of-day, day-of-week for weekly, day-of-month (1–28) for monthly, timezone, scope selection, retention count and destination.
- Destination: local path under the configured backup root, or S3-compatible (prefix, endpoint reference, credential reference from the secret store — the value is never stored in the panel).
- Verification: after each run, re-read every artifact and compare checksums; a `verify` action can re-run that check later. Optionally encrypted with a passphrase held in the secret store; when no store is configured the panel states clearly that archives are stored unencrypted.
- Restore: preview first (what will be replaced, counts, age warnings), part selection, typed confirmation, a mandatory safety backup immediately before the destructive phase, progress with a maintenance notice, result summary, and a full audit trail. Abort is possible until the import begins.
- Retention: `retain_until` per backup plus a prune task that never deletes the newest successful backup or one marked as protected.
- Status surfaces for other centres: last successful backup age (consumed by the security posture check) and disk usage of the backup root (surfaced in system health).

**Out**

- Point-in-time recovery and WAL archiving; cross-region replication; database failover; cluster-wide quiescing; per-tenant selective restore; restoring into a different installation (that is the import/export and air-gapped territory); scheduled restore drills; long-term archival tiering.

### Data model

**`backups`** — `id uuid pk default gen_random_uuid()`, `organization_id uuid null → organizations(id) on delete set null`, `label text not null default ''` (0–80), `kind text not null` (`manual|scheduled`), `schedule_id uuid null → backup_schedules(id) on delete set null`, `scopes text[] not null`, `status text not null default 'queued'` (`queued|running|succeeded|partial|failed`), `size_bytes bigint not null default 0`, `destination text not null default 'local'` (`local|s3`), `storage_prefix text not null`, `manifest jsonb not null default '{}'`, `checksum text null` (SHA-256 of the canonical manifest), `protected boolean not null default false`, `retain_until timestamptz null`, `error text null`, `created_by uuid null → users(id) on delete set null`, `created_at timestamptz not null default now()`, `started_at timestamptz null`, `finished_at timestamptz null`. Constraint: `cardinality(scopes) between 1 and 5` and every element in `('database','media','configuration','themes','plugins')`.

**`backup_parts`** — `id bigint generated always as identity pk`, `backup_id uuid not null → backups(id) on delete cascade`, `part text not null` (`database|media|configuration|themes|plugins`), `status text not null default 'queued'`, `item_count int not null default 0`, `size_bytes bigint not null default 0`, `checksum text null`, `storage_path text null`, `started_at timestamptz null`, `finished_at timestamptz null`, `error text null`. Unique `(backup_id, part)`.

**`backup_schedules`** — `id uuid pk default gen_random_uuid()`, `organization_id uuid null → organizations(id) on delete cascade`, `name text not null` (1–64), `frequency text not null` (`hourly|daily|weekly|monthly`), `at_time time null`, `day_of_week smallint null` (0–6), `day_of_month smallint null` (1–28), `timezone text not null default 'UTC'`, `scopes text[] not null`, `retention_count int not null default 7`, `destination text not null default 'local'`, `enabled boolean not null default true`, `last_run_at timestamptz null`, `next_run_at timestamptz null`, `last_backup_id uuid null → backups(id) on delete set null`, `created_by uuid null → users(id)`, `created_at timestamptz not null default now()`, `updated_at timestamptz not null default now()`. Constraints: `retention_count between 1 and 365`; `(frequency = 'weekly') = (day_of_week is not null)`, `(frequency = 'monthly') = (day_of_month is not null)`, hourly has no `at_time` requirement beyond being set for the others; unique index `(organization_id, lower(name))` plus one for the platform row where `organization_id is null`.

**`backup_settings`** — single row: `id smallint pk default 1 check (id = 1)`, `destination text not null default 'local'`, `local_root text not null default '/var/lib/omnion/backups'`, `s3_prefix text null`, `credential_ref text null`, `encryption text not null default 'none'` (`none|passphrase`), `default_retention int not null default 7`, `verify_after_backup boolean not null default true`, `updated_by uuid null → users(id)`, `updated_at timestamptz not null default now()`.

Indexes: `backups (created_at desc)`; `backups (status) where status in ('queued','running')`; `backups (retain_until) where protected = false`; `backup_schedules (next_run_at) where enabled`. Migration: `database/migrations/0013_backup_center.sql` (append-only, commented like `0009`).

### Events

**Emitted:** `backup.started`, `backup.completed`, `backup.part.failed`, `backup.failed`, `backup.verified`, `backup.restore.previewed`, `backup.restored`, `backup.schedule.updated`, `backup.deleted`. Payloads carry the backup id, scopes, sizes, duration and part-level status — never a content dump and never a credential.
**Consumed:** none required; schedules are driven by the backup worker's own timer, and `backup.completed` feeds the security posture check and the health storage overview.

Webhook relevance: `backup.completed` and `backup.failed` are prime subscriber events (ops alerting); `backup.restored` is high-signal and must be subscribable because it changes all content at once. Audit names use the `backup.*` namespace with actor, kind, scopes, sizes and destination.

### Acceptance criteria

- [x] `crates/backup` exists with part producers, checksum computation and the prune task, unit-tested. — **extended 2026-09-29 with `crates/backup/src/media.rs`**, which is the part this crate was silently not doing: it counted the library and recorded the count. `document_media` is gone, replaced by a copy loop over the deployment's own object store, 22 unit tests, proved by the walk below. — **shipped as `crates/backup/{part,destination,store,error}.rs`.** 46 unit tests, 0 failures, plus seven walks over the real router. Six decisions, each a shortcut that produces a plausible wrong answer:
  1. **A run's terminal state is DERIVED from its parts, never passed in.** `summarise()` reads them and `finish_run` takes no status argument, so a handler that returns early cannot record a success. Three tests exist only for this: four successes and one failure is `partial`, no part finished is `running` whatever the caller said, and one success among failures is still `partial`.
  2. **A part that produced nothing is still a part.** `Part::done("plugins", 0, 0, ...)` and `Part::failed("plugins", ...)` are different values, and `is_readable()` tells them apart. A manifest that listed only what worked could not answer the question the restore wizard asks first — *was media part of this run at all?* — which is why `verify_manifest` **skips** a part that never produced an artifact instead of reporting it unreadable, and a test pins that.
  3. **Verification compares checksum AND size.** A hash-only comparison passes the one corruption that matters — the artifact that lost its whole content, because the SHA-256 of an empty body agrees with itself. The test builds exactly that case.
  4. **The manifest's checksum covers the manifest alone.** A checksum that mixed in the parts would change on every re-verify, so `verify` would report a mismatch against the run it had just confirmed. The canonical form sorts the parts, so two runs that produced the same artifacts in different orders hash the same.
  5. **Keys are relative to the run's prefix, never absolute**, and the prefix is normalised once — without that, `backups` and `/backups` write to two different directories and only one of them is the one the screen showed.
  6. **The destination probe WRITES, READS BACK and REMOVES.** A read-only probe passes on exactly the configuration that fills up at 02:00, and a store that accepts the write but refuses the delete is reported as **failing**, because that store accumulates one marker per probe.
  Two PostgreSQL facts the tests forced out: a `check` constraint may not contain a subquery, so array uniqueness goes through an IMMUTABLE wrapper function that takes the array as an argument; and `values` is reserved in a function parameter list, so that wrapper's parameter is spelled `items`.
  **The prune candidates are decided in the one statement that feeds the delete** — past `retain_until`, not protected, not still in flight, and not the newest successful — so a caller cannot express a third rule that disagrees with it.

- [x] Artifacts exist at the configured destination with the recorded sizes and checksums. — **this criterion caught the worst defect of the slice.** The first implementation built each part's document, hashed it and recorded a `done` part — and **no code path ever wrote the bytes to disk**. The run reached `succeeded` with five artifacts that did not exist, and `verify` answered "could not be read back: configuration, database, media, plugins, themes" for all five. A unit test on `bytes_checksum` cannot see it: a checksum over a document nobody wrote is a perfectly good checksum, and nineteen tests would have accepted it. Only a walk that uploads, then re-reads the file off the destination, can see that the two halves are different facts. The producer now writes the bytes **before** recording the part, and a write failure is a **failed part** rather than a success with a good checksum. The walk asserts, for each of the five parts, that the file exists and that its length equals the recorded size.
- [x] The `media` part copies the library's bytes, and a part that could not copy all of them fails the run. — **this criterion is the one the slice was missing, and finding it changed what "done" meant for the other four parts.** `document_media` ran `select site_id, count(*), sum(size_bytes) from media` and wrote *that* as the part's artifact: the run reached `succeeded`, `verify` agreed with its own checksum, and no library byte had been copied anywhere. The mask is what makes it worth writing down — **counting is what the database can do with the object store switched off**, so the count was available on exactly the run where the store was unreachable, and it is the number that made the row look healthy. `crates/backup/src/media.rs` now copies every object through the deployment's own `Storage` abstraction (never a vendor SDK, so a directory-backed site and a bucket-backed site both work), one at a time, re-hashing the bytes that come back and comparing size **and** SHA-256 with the library row — a disagreement is a failure, never a quiet copy. An object over 256 MiB is **named and skipped rather than truncated**, because a truncated image is a backup that claims to have restored a file it destroyed. `the_media_part_copies_the_librarys_bytes_and_a_missing_object_fails_the_run` proves both halves: two real objects uploaded through `state.storage()` and read back off the destination byte for byte, then a row whose object the store does not have, after which the run must be `partial` with `1 of 3` in the error — never `succeeded` with two of three files.
- [x] A run's artifacts land at the path its own manifest records. — **found by the walk above, in code this loop shipped a slice earlier.** Every artifact was written to `<root>/<prefix>/<prefix>/…`: a storage key is already prefix-qualified, and the writer joined it to `local_root_for(root, prefix)`, which adds the prefix again. The **verify reader doubled it the same way and the suite's path helper did too**, so all three agreed, all eight walks were green, and the archive sat one directory deeper than the manifest said. Three halves making the same mistake is not a cross-check — the same lesson as the media part itself, one level down. Fixed with a separate `local_path_for(root, key)` ("a key is absolute with respect to the root") and a unit test that writes the wrong path out in full so it cannot return quietly. The walk now reads the archive's location **out of the index the run wrote** rather than recomputing it, so the two halves can disagree.
- [x] `verify` re-reads artifacts and reports a mismatch by flipping the backup to `failed` with detail. — **partly proved; the flip is slice 2's.** `verify_manifest` distinguishes three outcomes and the walk proves two of them over the real destination: a clean run answers `200` with `clean: true` and names the matched parts, and a **truncated** artifact answers `200` with `clean: false`, `mismatched: ["media"]` and a summary naming the part. A mismatch is a verdict and not an exception — a `500` would say "verification broke" instead of "the media artifact is 7 bytes". **What is not yet done:** flipping the backup row to `failed` on a mismatch. That belongs with the restore path, because a verify that rewrote the row would destroy the record of what the destination held at the time, and the manifest is the only copy of that.
- [x] Manifest JSON is downloadable and matches the artifact listing. — `GET /api/v1/backups/{id}/manifest` returns the stored manifest, and the detail screen has a `Copy manifest` button. The manifest is a **snapshot**: it records what the parts were when they were produced, so reading it back after a restore describes the artifact rather than the platform. Its `checksum` covers the canonical form of the manifest alone, never the parts — a checksum that mixed them in would change on every re-verify and the verify would then report a mismatch against the run it had just confirmed.
- [x] Backup detail shows every part, its timing and its error state when present. — `GET /api/v1/backups/{id}` returns the run, its parts and its manifest, and the admin detail panel renders all three. Each part row carries its status, its item count, its size **right-aligned and tabular** (a size column that jitters as digits change reads as a different number), and a note that is either the failure message or — for a part that produced nothing — the literal sentence "nothing to record — this is a result, not a gap". The manifest checksum is shown beside the header so an operator can quote it. `restorable` is its own field rather than a derived `disabled`: "this part did not produce an artifact" and "this part produced one you may not read" are different answers to the same button being off.
- [x] Restore preview lists counts, the backup age and warnings without touching live data. — **shipped as `crates/backup/src/restore.rs` + `crates/backup/src/preview.rs` + `GET /api/v1/backups/{id}/restore-preview`** (behind `backup.read`, not `backup.restore`: reading a warning changes nothing, and gating it behind the destructive key means an operator's first sight of this screen is a 403 that never showed them what they were agreeing to). The decisions live in a **pure** module so the rules are unit-tested with no stack, and the live-data comparison is a separate one so a change in how it is counted cannot silently alter which warnings fire. Four things this criterion turned out to be asking: (1) **the number that matters is about LIVE data, not the archive** — 3 archived objects replacing a 4 000-object library and 4 000 replacing 3 are the same manifest, and only the live counts tell them apart, so `data_loss` is a `danger` and a fully-covered part is silent; (2) **a part that is not provably present is not offered** — availability needs a `done` part AND an artifact whose re-read size agrees with the manifest, so a `partial` run offers its good parts and names the rest rather than answering "no" to a run that lost one small part; (3) **the typed phrase is a hash of the run id, not a slice of it** (see the v7 defect below); (4) **a bounded comparison must report its own truncation** — the media key comparison caps at 5 000 and says so, because a bounded safety check that quotes a truncated number is a false reassurance. Proved by three walks over the real router: the preview prices a one-file archive over a two-file library at exactly **one** loss and writes **nothing** (parts, status, prefix, finish time, media rows and the archive on the destination are byte-identical before and after, read back out of PostgreSQL rather than from the response); a **truncated** artifact is refused and **no phrase is issued at all**; and a stranger's run is a 404 that does not name the tenancy rule, so the preview is not a restore-point oracle across tenants. The panel is collapsed until asked for, draws each warning at its own severity, leads with the number of live items that would be lost, and shows the confirm phrase before anything requires it. **No restore button yet, deliberately** — the safety backup and the abort path ship first, and a button that could not be pressed is a dead button.
- [x] Restore from the wizard restores the selected parts and writes a `backup.restored` audit entry. — **the `media` half shipped** as `crates/backup/src/restore_objects.rs` + `POST /api/v1/backups/{id}/restore` + the restore control on the preview panel. Five decisions, each a shortcut that produces a plausible wrong answer:
  1. **An object is re-hashed against the index's own checksum BEFORE it is written.** The backup half had this defect once — a run that copied nothing and recorded a checksum over a document nobody wrote — and reading it from the other end is the same mistake in a mirror: a corrupt object written first and checked afterwards leaves a wrong file in the live library with a correct-looking row, and the only repair is a second restore. The walk truncates a real object on the destination and then asserts the **live store still holds its own bytes**, compared as bytes rather than by length, because a length check passes by accident on an overwrite.
  2. **The library row is keyed on `storage_key`, never on the archive's `id`.** The id was the row's id at backup time; a file uploaded since got its own, so writing the old id back would resurrect a trashed file or collide with a live row. It is scoped by organization in the **same `where`**, because a restore that wrote a stranger's row is the media-part leak again, read backwards.
  3. **A selection is narrowed, never widened.** An unknown part name is refused rather than dropped, because a request for `["database", "typo"]` that silently restores `database` is a restore that did less than it was asked and reported success. The parts are restored in **manifest order**, not request order, so objects never land before the schema they hang off; a duplicate in the selection restores once.
  4. **Nothing is deleted by a restore.** The archive is added to the library, and a file uploaded after the run is *priced* by the preview rather than removed here. `MediaRestoreReport::dropped` exists and is zero by construction, because a field that *could* hold a value is a field somebody will fill in somewhere quieter.
  5. **The index's version is checked, and the check is not a formality.** `MediaIndex` is serde, and serde's default is to accept a missing field as its `Default` — so a v2 index read by this build would deserialise into an empty object list and the route would answer "0 objects restored" for a full archive. A success that restored nothing is the one sentence this feature must never produce. An index with an unknown **extra** field is still read, because that is what forward compatibility looks like.
  **The `database` part is refused by name, and that is the honest answer** — it records a row COUNT per table, which is an inventory and not a dump, so restoring it would replace the platform's schema with an inventory of it. That is the counting defect this crate was written to remove, in its most expensive form; the route refuses it in a sentence an operator can act on rather than quietly doing nothing. This line is therefore **partly open**: the other four parts are recorded and priced but not applied, and the panel names the difference between "restored" and "reported".
  Proof: **eight walks over the real router, 0 failures.** The object is really back in the live store and the file uploaded after the run is still there (a "replacement" implementation fails that assertion, and it is the one that matters: an operator who restores a week-old archive and loses Tuesday's upload has no way back that the safety backup does not have to cover). - [x] An encrypted archive verifies with the stored passphrase and fails cleanly with a wrong one. — **shipped this tick in two commits (`4586277e`, `abb1e101`), and the criterion was narrower than it looks.** The settings row has carried `encryption in ('none','passphrase')` since migration `0157`, and *nothing read it*: an operator could select passphrase mode, the screen would save it, and every artifact would still be written as plain JSON on the destination. The constraint was the whole feature.

  **The cipher (`crates/backup/src/crypto.rs`).** An artifact is `OMN1 ‖ salt(16) ‖ nonce(12) ‖ AES-256-GCM`, keyed by `HKDF-SHA256(salt, passphrase, info="omnion-backup/artifact/v1")`. The magic is authenticated **as AAD**, so a ciphertext cannot be relabelled as plaintext or the reverse — and it is what lets a wrong passphrase answer *a dirty key is not corruption*: `open` checks the framing from the bytes alone and reports `NotEncrypted` separately from `Undecryptable`. Two decisions are the reason this is not a base64 blob: the salt is **per artifact**, so two archives of identical content do not share a key; and the `info` label namespaces the derivation, so an S3 credential that happens to be the same string cannot decrypt an archive.

  **The seam.** `resolve_passphrase(ref, reader)` is the only place that touches the secret store, and it takes a reference plus a closure — this module has no store dependency and no way to invent a passphrase. The migration's own comment says the table has no column a value could be written into, and nothing here changes that.

  **The producer and the verifier now agree on what a part *is*.** One rule, applied to two fields: the manifest describes the **document** (its checksum *and* its size), while the bytes that land are `document + framing + GCM tag`. `observe` opens the artifact before hashing. Recording either field from the sealed bytes made a correctly-encrypted archive report *"checksum differs for 1 part"* on its very first verification — the new walk found it, not reasoning: right passphrase, right bytes, one number describing something else.

  **A configured-but-unresolvable passphrase fails the run rather than falling back to plaintext.** `PUT /backup-settings` refuses the mode by name (naming the variable to set) when the reference does not resolve, and stores nothing; the producer fails every part with the sentence that says why. The panel's own *"archives are stored unencrypted"* line is the reporting half; this is the enforcement half, and it is in the API because the mode can also be chosen by anyone editing the row.

  **A sealed artifact with no key is skipped, not reported as corrupt.** It is not unreadable (the bytes are there) and it is not a mismatch; the verdict stays `clean: false` because something was not checked. Reporting a mismatch would send an operator to restore a perfectly intact backup.

The salt was therefore untested while the comment beside it claimed the salt was the property that stopped two identical archives from matching. The claim needed the nonce held fixed, and the salt now has two assertions that say so (`the_salt_alone_changes_the_key_of_an_otherwise_identical_artifact`, `the_nonce_is_fresh_per_artifact_and_is_not_the_salt`); that regression fails as it should. This is the "a test that cannot fail is worse than no test" class, found by *regressing the thing the comment claimed* rather than by reading the test.

- [ ] Schedules for all four frequencies save, show a computed next run and fire within one tick of it. — **the cadence and the worker both shipped this tick; the four-frequency form and the browser pass are still open.** The defect this criterion was hiding is the same class as the uncalled `prune_candidates` one layer up: `backup_schedules` shipped in slice 1 with a `next_run_at` column and `next_due_schedules` shipped with it, and **nothing ever wrote the column or called the query** — so a schedule could be created, listed, and rendered with a cadence sentence beside an empty next-run cell for ever. An unknown zone is refused by name rather than defaulted to UTC — "every day at 02:00 (Europe/Istanbool)" is not a fallback, it is a wrong answer delivered confidently.

Both were found by three zone tests failing against a version that trusted it. A gap moves the run forward by the gap (the same reading once the clocks have jumped — dropping it loses a backup, rejecting it stops the schedule for a year); a fold runs **once, at the earlier** of its two readings, because running on both would produce two runs an hour apart for one instruction and `retention_count` would hold two of the same backup.

### Risks / notes

- The database export must be consistent: take it inside a transaction with a stable snapshot, and refuse to write a partial artifact as if it were complete.
- Restore is the most destructive operation in the platform: it always previews first, always takes a safety backup, always demands the typed confirmation, and always audits. Nothing may shorten that path for convenience.
- Never store a passphrase, endpoint credential or S3 key in the panel or the repo — only a reference; when the secret store is absent, the UI says the archive is unencrypted instead of pretending.
- Media copies can be large: stream object-to-object rather than buffering, cap concurrent copies, and record progress so a long media part does not look hung.
- Restoring plugins can invalidate running workflow executions; the result summary must say what was restored and operators are expected to reconcile afterwards.
- Clock and timezone bugs in schedules are the most likely defect: compute next run in the schedule's timezone, store UTC, and cover the daylight-saving transition in tests.
