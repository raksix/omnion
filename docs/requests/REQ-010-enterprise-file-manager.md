# REQ-010 — Enterprise File Manager

> **Status:** in-progress (slice 3 closed; slice 4 next) · **Captured:** 2026-09-25 · **Layer:** core (`crates/media`) + admin UI
> **Source:** owner brief — platform feature pool (2026-09-25)

## Request

A much more advanced version of the Media Library:

- folders
- permissions
- version history
- file preview
- metadata
- image transformation
- video preview
- PDF preview
- CDN
- S3
- duplicate detection
- virus scanning
- retention policies

## Implementation spec

> **Where:** `crates/media` (model, folders, versions, transformation, scan, retention) on top of `crates/storage` (object store abstraction: MinIO in development, any S3-compatible endpoint in production) · **Migration:** `database/migrations/0015_file_manager.sql` (next free slot at build time), extending the `0005_media.sql` table whose own comment already points forward to this request · **Admin routes:** `/media/*` (the existing library screen becomes the browser) · **Permission family:** `media.*` · **Depends on:** `crates/permissions` (folder grants reuse the IAM subject model, docs/07), `crates/audit`, `crates/events`, `crates/ai-hub` (optional alt-text assistance), REQ-011 for CDN purge, REQ-013 for backup inclusion.

### Scope (in / out)

**In**

- **Folders:** a per-site folder tree (create, rename, move, delete) with drag & drop, breadcrumbs and a slide-over tree on small screens; moving a folder or file never changes the storage key of the files inside.
- **Browser:** grid and list views, lazily generated thumbnails, multi-select with a bulk bar (move, tag, copy, download as archive, delete, restore), search and filters (kind, size, uploader, date range, tag, scan state, has-versions), sorting and a trash with a countdown.
- **Version history:** replacing a file creates a new version with its own storage key, checksum, size and author; any version can be downloaded; restoring an older version creates a newer one rather than rewriting history; text versions can be diffed.
- **Preview:** image (zoom, pan, fit/actual size, EXIF summary), video (poster frame, HTTP range streaming, captions when present), audio (player plus a waveform thumbnail), PDF (paged viewer), text/code (monospace with a line cap); unsupported types fall back to a download card with a file-type illustration, never a broken frame.
- **Metadata:** alt text, caption, description, tags, custom key/value pairs (`metadata jsonb` with a GIN index), EXIF/audio-tag extraction on upload, stored dimensions, duration and page count, and a metadata filter in the browser.
- **Image transformation:** named presets (width, height, fit `cover`/`contain`/`fill`, format `webp`/`avif`/`jpeg`/`png`, quality, optional watermark, optional blur placeholder) served on demand through a URL contract (`/api/v1/media/{id}/raw?preset=card`) with a content-addressed cache key so a CDN can hold results for a year.
- **Storage and delivery:** per-site storage settings (endpoint, region, bucket, path prefix, public/private default, signed-URL lifetime), a configurable public base URL, purge-on-replace through REQ-011, and a connection test that proves read/write with credentials held by reference.
- **Duplicate detection:** checksum grouping inside a site (optional cross-site search for platform owners), a report with reclaimable size, and a merge that keeps one file, repoints every reference and trashes the copies.
- **Virus scanning:** uploads enter `pending`, a scanner checks out of band, results are `clean`/`flagged`/`skipped`/`error`; flagged files are quarantined and not downloadable, an event fires, and an admin can release or delete them; an unreachable scanner never loses an upload, only blocks serving.
- **Permissions and sharing:** folder and file grants over the IAM subjects (user, group, role) with read/write/delete/share capability bits, inheritance down the tree with per-node override, and public share links with expiry, an optional password, a download counter and immediate revocation.
- **Retention and references:** policies (scope site or folder; keep versions N days; move to trash after N days; purge after N days; legal hold bypass) applied by a daily worker that records every run, a trash countdown in the UI, and a `media_references` table (maintained on publish plus a repair scan) that answers “used in” and makes purge refuse to delete a file still in use.

**Out (tracked elsewhere)**

- CDN adapters, cache rules and the purge queue → REQ-011; bucket backup/restore → REQ-013; quotas and storage billing → REQ-005/REQ-024.
- Document management (approvals, contract folders) → REQ-058; AI-generated alt text → REQ-042; PDF text extraction into the search index → REQ-002; the antivirus engine choice and its operations stay a pluggable scan client, not a bundled engine.

Checks: `quality between 1 and 100`, `keep_versions_days >= 1`, `purge_after_days >= trash_days`, `fit in ('cover','contain','fill')`, `format in ('webp','avif','jpeg','png')`, `subject_kind in ('user','group','role')`, `scan_status in ('pending','clean','flagged','skipped','error')`. Indexes: `media_folder_idx (site_id, folder_id, created_at desc)`, partial `media_live_idx (site_id) where deleted_at is null`, `media_trash_idx (site_id, deleted_at desc) where deleted_at is not null`, `media_checksum_idx (site_id, checksum)`, `media_scan_idx (scan_status) where scan_status = 'pending'`, GIN on `metadata` and `tags`, `media_versions_media_idx (media_id, version desc)`, `media_shares_token_idx (token_hash)`.

Migration `database/migrations/0015_file_manager.sql` — append-only and commented in the `0005` style; it alters `media` with nullable columns only (existing rows read as `pending`, no folder, version 1), creates the new tables, backfills `version_count = 1` and `metadata = '{}'`, and seeds one `Standard` transformation preset plus one default retention policy per existing site.

### Events

- Emitted: `media.uploaded`, `media.updated`, `media.version_created`, `media.deleted`, `media.restored`, `media.purged`, `media.duplicate_merged`, `media.scan_clean`, `media.scan_flagged`, `media.scan_error`, `media.share_created`, `media.share_revoked`, `media.retention_applied`.
- Payloads carry ids, filename, size, checksum, folder path and scan state — never file bytes, never a share token or password. Consumed: `page.published` refreshes reference rows for the page’s media; `site.deleted` moves that site’s files to the trash rather than purging them.
- Webhook relevance: `media.version_created` and `media.purged` trigger the CDN purge (REQ-011); `media.scan_flagged` raises a security notification (REQ-012/REQ-021) and keeps the share route closed until release; automation rules may react to new uploads (for example generating derivatives).

### Acceptance criteria

- [x] `0015_file_manager.sql` applies on a fresh database and on one with existing `media` rows; `cargo test -p omnion-media` is green. — shipped as **`0025_file_manager.sql`** (0025 was the next free slot on `main`; siblings hold 0019/0020/0021/0022/0023/0024 in their own branches). Applied against a database seeded with three `media` rows: rows untouched, `version_count = 1`, `scan_status = 'pending'`, `metadata = {}`, `updated_at = created_at`, one root folder materialised, 16 indexes. Also applied across the whole migration set on a fresh database. `cargo test -p omnion-media --lib` → **22 tests, 0 failures**.
- [x] Folder create, rename, move and delete work; deleting a non-empty folder asks and behaves exactly as the confirmation text says. — create, rename, move and delete are all on the screen and in the API. The confirmation states the refusal ("A folder that still holds files or subfolders is refused") and the API agrees: `delete_empty_folder` counts children and files and answers `folder_not_empty` with the count; the walk proves **both** sides of that rule, the refusal with a folder holding a subfolder and the acceptance with an empty one. A move rewrites the path of the whole subtree (the walk moves a parent and reads the child's new path back out of the row), refuses a cycle with `folder_cycle`, and a move to where the folder already is is a no-op rather than a bogus cycle. **Six real defects were found and fixed by this walk**, all of them invisible to the layers that owned them: a filter that wrote its placeholder twice, `make_interval` with a bound parameter, a `sum(bigint)` sqlx cannot decode, an `ORDER BY` inside `UPDATE`, a parent resolved by the moved folder's *own* new path (so every move self-parented and the first pull-to-the-root hit the root's unique index), and an omitted `parent_id` silently meaning "move to the root" instead of the documented "keep the current one".
- [x] List and grid views share the selection; filters (kind, size, uploader, date, tag, scan state, has-versions) combine and the count matches the returned rows. — grid and list read the same `selection` array. The store builds its `where` clause and its binds from **one** filter list (`push_filters`), so `count(*)` and the page cannot disagree; the footer reads "Showing N of TOTAL" from that total. The walk drives a folder listing, a kind filter, a search term containing a `like` wildcard and a subfolder listing over the real router, and each one is now proved *against the statement the builder actually emits* — `a_filter_never_writes_its_placeholder_twice` walks every filter and every combination and fails on `$$`. **Partly open:** kind, search, scan state, has-versions and the subfolder toggle are on the toolbar; size, uploader and date-range filters are in the API and the store but not yet on the toolbar (they arrive with the metadata screen in slice 2, where they are edited against).
- [x] Bulk move, tag, copy and delete apply per item and report partial failures; delete moves to trash and never purges. — `POST /api/v1/media/bulk` answers `{requested, changed, failures[]}`; a file of another site or a stale id is a **per-file** failure, so forty good files still get processed. `delete` only sets `deleted_at`; `purge` is a separate action and a separate route, and the bulk confirmation says the files can be restored.
- [x] A replacement creates version N+1 with its own storage key and checksum; the previous version stays downloadable and restoring it creates a newer version. — shipped as **`0026_media_versions.sql`** + `crates/media/versions.rs` + `apps/api/src/routes/media_versions.rs`. The history is append-only: a replace writes `sites/{site}/{media}/v{n}.{ext}` and leaves the old key exactly where it was, so a page that has cached it is still correct; a **restore copies the old bytes to a new key and appends the copy**, so version 1 means the same bytes today as it did yesterday. The number comes from the database under a row lock on the `media` row, never from the caller, so two concurrent replaces cannot both claim 4. Three walks over the real router prove it: a replace leaves version 1 downloadable and **byte-identical** (compared, not length-checked — a length check would pass by accident on an overwrite), the row points at the version it serves, the three keys are three keys, a download of an old version is an attachment named `hero-v1.png`; a restore appends version 3 with version 1's checksum while version 1 and version 2 are both untouched; and the routes refuse without a session, without `media.read`, and name a missing version by number.
- [ ] Image preview zooms and pans, video plays with range requests and a poster, PDF renders pages, text previews cap lines with a “download for the full file” hint, and an unsupported type shows a download card. — **done.** `features/media/file-preview.tsx` picks the renderer from the *content type*, never the extension, and routes SVG to the download card on purpose (it can carry script). Image: zoom 10 %–800 % as a transform, drag-to-pan above 100 %, and an `onError` that replaces a broken frame with a card naming the cause instead of a broken-image glyph. Video: `preload="metadata"` so a 400 MB file is not pulled to draw one frame. Audio: player plus the duration the header carried. PDF: the browser's own viewer plus the page count. Text: loaded on demand behind a button (a 5 MB log has no business in the initial payload) and capped at 200 lines with a line that says how many were left. Anything else: a download card with the type, the size and — when previewing an old version — a way back to the current one. **Range requests on the raw path are not implemented**: the platform read path answers the whole object, so a video seeks by re-fetch rather than by range. That is recorded as open for slice 3, where the CDN and the transformation cache arrive and the serve path is rewritten anyway.
- [x] `?preset=card` returns the configured size and format, results are cached by content hash, the key changes when the preset changes, and an unknown preset falls back to the original. — **shipped** as **`0027_media_transforms.sql`** + `0028_site_presets.sql` + `crates/media/{transform,pixels,preset_store}.rs` + `apps/api/src/routes/media_transform.rs` + `features/media/presets-view.tsx` + `/media/settings`. A preset **produces real pixels**: `crates/media/pixels.rs` decodes, resamples and re-encodes, and every extractor refuses rather than guessing. Four decisions the tests forced out of the implementation, each a shortcut that produces a plausible wrong answer:
  1. **A request never enlarges.** A 2400px request against a 1200px source is refused with an explanation, not answered with a blurry upscale that is larger than the original. The check is `>`, not `>=` — asking for exactly the source's own size is the identity, and a template that names the same number twice is not an error.
  2. **`contain` letterboxes and `cover` crops.** The first version shared `cover`'s resampler and produced a correctly-sized *crop*, which passes a square-crop assertion and is wrong on every non-square source. A `contain` result is pasted onto a canvas of the box's size, so a thumbnail is a stable 320×320 and not a 320×180 that shifts the layout per image.
  3. **A missing dimension is derived, never defaulted.** `?w=300` on a 1200×630 hero is 300×158; defaulting the height to the width turns a 16:9 hero into a square on every page that forgets to name both.
  4. **Transparency is a decision.** A transparent source emitted as JPEG is composited onto a declared background rather than having its alpha dropped, which is what puts black fringes around a logo.
  The cache key is `sha256(source checksum | canonical recipe)` with a **NUL** separator, and every pixel-changing field is in the canonical form — including quality, the one people forget, because editing a preset and keeping its name must not serve the previous quality's pixels under the new name. The key is a pure function of its inputs, which is what lets a CDN hold the object for a year; the response says `max-age=31536000, immutable`. An edit leaves the old row in place: its key still matches its pixels, so a page cached against it is still correct.
  **Three defects found by the walks over the real router, none of which a unit test on `transform_bytes` could have seen:** the derivative header carried the *object* key where the identity belongs (a caller reading it and looking it up in `media_derivatives.cache_key` found nothing — the two are different strings, and the response builder took one parameter where it needed two); **a site created after the migration got no `standard` preset**, so a page already asking for `?preset=standard` would silently fall back to full-size originals — on new sites only, which is where nobody looks, and fixed as a trigger rather than in the create path because onboarding, the tenancy API and a future import all insert the row themselves; and a test asserting "the first call builds" **passes once and fails for ever after**, because the row is keyed by the source bytes and a re-run reproduces them exactly.
  Proof: 5 walks over the real router, 0 failures — the bytes are compared as bytes and decoded again rather than length-checked (a length check passes by accident on an overwrite), the second request is **byte-identical** to the first, the object is read back out of the store and compared to what was served, the old row survives an edit, a delete cascades the cache away, an unknown preset returns the original *byte for byte* with no derivative key, an SVG answers `not_transformable` naming the type, and every preset field error names its field. `cargo test -p omnion-media --lib` → **78 tests, 0 failures**; the pre-existing `--test media` → **11 walks, 0 failures** unchanged against the modified raw route. `media.settings.manage` is a new permission key, deliberately separate from `media.manage`: a reader may list the presets (the browser shows a picker on every image) and may not create one.
- [x] Metadata and tags round-trip and are searchable; EXIF, duration and dimensions are filled for supported types on upload. — **metadata and tags: done.** The detail screen's Metadata tab edits alt text, caption, description and tags against the existing `PATCH /api/v1/media/files/{id}` and saves with a per-field labelled form; the tab repaints from the row after a restore, so a restored version never shows the previous one's alt text. **dimensions and duration: done** — `crates/media/probe.rs` reads them out of the file header for PNG, GIF, JPEG, BMP, TIFF, WebP (all three containers), MP4/QuickTime, WebM, WAV, MP3, Ogg and PDF, from a 64 KB prefix and never the whole file. **EXIF: done** — shipped as **`0042_media_exif.sql`** + `crates/media/src/exif.rs` + the `exif` column on `media`. Six decisions, each a shortcut that produces a plausible wrong answer:
  1. **A TIFF header is not EXIF.** The IFD format is shared by TIFF itself, by GeoTIFF and by half a dozen camera makers' proprietary blocks. What makes the block EXIF is the `Exif\0\0` signature inside a JPEG `APP1`, an `EXIF` chunk in a WebP or an `eXIf` chunk in a PNG — so the container is checked before any TIFF parsing runs.
  2. **Nothing is read from outside the prefix.** Every field's value may be an *offset* into the block, and an offset is attacker-controlled. Every read is a range request whose failure is the answer, not a panic; a count that would overflow its width is refused rather than wrapped into a small number that reads the wrong bytes plausibly.
  3. **A rational with a zero denominator is absent, and `1/200` is *not*.** The first guard refused the normal case (`den > num`) and kept the corrupt one — the exact inversion, which is how a reader ends up with no shutter speed on every photograph and a divide-by-zero on the one broken file.
  4. **Orientation changes the box, not the file.** Values 5–8 store the picture sideways and browsers rotate it themselves, so a grid reserving `width × height` reserves the wrong box and shifts every image below it. The stored columns carry the *oriented* pair, the raw value stays in the record so a downloader does not rotate twice, and the API sends both readings: `display_width`/`display_height` for a layout and `width`/`height` for a version list.
  5. **A GPS fix is a flag, never coordinates.** The record says `gps: true` and the type has no field a coordinate could occupy, so a media library cannot quietly file an operator's home address into a row that search, an API key and a share link can all read.
  6. **A replacement *replaces* the record.** A screenshot uploaded over a camera original must not keep claiming to have been shot on a body it was never near; a file with no block clears the column rather than inheriting the previous version's, and the column is null rather than `{}` so "we never read a block" and "the camera said nothing" stay two rows in a report.
  **Also shipped here:** the Metadata tab's **Camera** block — a block rather than three more rows, because a photograph either has a camera record or has none and a list of always-empty cells reads as a file with nothing in it. The shutter prints as `1/200 s` and past a second as a decimal, the lens and the body are separate rows, and the GPS line states the omission rather than leaving an editor looking for a map pin that is not there.

Both walks read the column **out of PostgreSQL**: a response that omits a field is indistinguishable from one that stored it and chose not to say so. ### Risks / notes

- **Migration number** is “next free slot at build time”; the `media` alterations must stay nullable so existing rows keep working without a stop-the-world backfill.
- **Storage keys are immutable:** a move changes the folder reference, never the key, and a replace writes a new key — anything else breaks caches and signed URLs.
- **Transformation is on demand with a cache**, never a pre-generated matrix (presets × files would explode); cache keys include a hash of the preset definition.
- **Public delivery and privacy:** private files only through signed URLs or a share token, the public base URL is per site, and the settings screen states bucket visibility explicitly so a world-readable bucket cannot happen by accident.
- **Scanning is best-effort at ingest, strict at serve:** a scanner outage must not lose uploads, but an unscanned file must not be publicly readable until it clears.
- **Retention is destructive:** every rule change and run is audited, purge is soft-first (trash) then hard after the window, and legal hold wins over all other rules.
- **Reference bookkeeping is the weakest link** — a repair scan exists from slice 4 and is runnable from Settings, so “used in” can be trusted and purge refusals are not spurious; streamed `.zip` downloads of large selections need backpressure and a selection cap.
